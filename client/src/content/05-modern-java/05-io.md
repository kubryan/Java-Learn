# I/O｜輸入輸出、Path、Files 與文字檔案

> **核心目標：** 能夠安全地讀取、寫入、列出與管理檔案，並理解 `Path`、`Files`、`InputStream`、`OutputStream`、`Reader`、`Writer`、`BufferedReader` 與 `BufferedWriter` 各自處理哪一層問題。

Java I/O（Input／Output）是 Java 存取外部資源的 API 集合，外部資源包含檔案系統、網路與其他資料來源。[1] 對 JavaBase 而言，這不只是抽象知識：本地 Markdown Workspace 需要讀取 `.md` 檔案、掃描目錄、建立或更新原稿、處理 UTF-8 文字，還要避免相對路徑逃出 workspace 根目錄。

這篇先掌握最常用的檔案 I/O，不深入 `FileChannel`、`AsynchronousFileChannel`、自訂 `FileSystemProvider` 或完整 NIO.2 進階設計。學完後，你應該能讀懂大多數 Java 專案中的檔案載入器、設定檔處理器、資料匯出器與 Markdown indexer。

## 學習完成標準

| 能力 | 完成後你應該能做到 |
|---|---|
| 路徑建模 | 使用 `Path` 表達檔案位置，避免到處拼接字串 |
| 檔案操作 | 使用 `Files` 檢查、建立、讀取、寫入、複製、移動與刪除檔案 |
| 文字 I/O | 使用 UTF-8 與 `Reader`／`Writer` 讀寫文字 |
| 二進位 I/O | 知道何時使用 `InputStream`／`OutputStream` 處理 bytes |
| Buffered I/O | 理解 `BufferedReader`／`BufferedWriter` 如何包裝底層 Reader／Writer |
| 資源管理 | 用 try-with-resources 確保 stream、reader、writer 關閉 |
| Workspace 實戰 | 讀取 Markdown、掃描 `.md`、安全解析相對路徑並原子化替換原稿 |

## 1. File I/O 的基本模型

### 檔案、路徑與資料流不是同一件事

| 名稱 | 角色 | 典型 Java API |
|---|---|---|
| File I/O | 對檔案與目錄進行輸入輸出 | `Files.readString`、`Files.writeString` |
| `Path` | 描述檔案或目錄的位置 | `Path.of(...)`、`resolve(...)` |
| `Files` | 對 `Path` 執行檔案系統操作的 static utility class | `exists`、`copy`、`move`、`walk` |
| `InputStream` | 逐步讀取 byte | `Files.newInputStream(...)` |
| `OutputStream` | 逐步寫入 byte | `Files.newOutputStream(...)` |
| `Reader` | 逐步讀取 character | `Files.newBufferedReader(...)` |
| `Writer` | 逐步寫入 character | `Files.newBufferedWriter(...)` |
| `BufferedReader` | 具備 buffer 的文字 Reader | `readLine()`、`lines()` |
| `BufferedWriter` | 具備 buffer 的文字 Writer | `write()`、`newLine()`、`flush()` |

現代 Java 檔案程式通常以 `Path` 加上 `Files` 為入口，而不是把路徑當成普通字串。`Path` 負責路徑的組合、解析與比較；`Files` 提供對檔案系統真正執行讀寫與管理的操作。[2]

```java
Path workspace = Path.of("workspace");
Path note = workspace.resolve("java").resolve("io.md");

if (Files.exists(note) && Files.isRegularFile(note)) {
    System.out.println("Markdown exists: " + note);
}
```

### Java I/O 的例外

許多檔案操作會丟出 checked exception `IOException`，因為檔案可能不存在、權限不足、磁碟錯誤、路徑指向目錄或編碼轉換失敗。呼叫端必須處理或宣告它：

```java
static String readTitle(Path path) throws IOException {
    return Files.readString(path, StandardCharsets.UTF_8);
}
```

更具體的例外可能是 `NoSuchFileException`、`FileAlreadyExistsException`、`AccessDeniedException` 或 `NotDirectoryException`。初學時可以先捕捉 `IOException`，但在需要顯示精準錯誤訊息或提供不同 recovery strategy 時，再捕捉更具體的子類別。

## 2. `Path`：正確表示檔案位置

### 建立 Path

`Path` 是介面，常用 `Path.of(...)` 或 `Paths.get(...)` 建立。`Path.of` 是較新的簡潔寫法；實際路徑分隔符號由作業系統與 file system provider 處理，不要自己假設永遠是 `/`。

```java
Path relative = Path.of("notes", "java", "io.md");
Path absolute = relative.toAbsolutePath();
Path normalized = absolute.normalize();

System.out.println(relative.getFileName()); // io.md
System.out.println(relative.getParent());   // notes/java
```

`Path` 可以是 relative path 或 absolute path。relative path 的意義取決於程式當下的 working directory，因此需要長期保存、跨執行環境比較或做安全檢查時，通常先轉成 absolute path 再 `normalize()`。

### `resolve`、`normalize` 與 `relativize`

不要使用字串串接路徑：

```java
// 不建議：容易漏掉分隔符號，也不表達路徑語意
Path wrong = Path.of("workspace/" + category + "/" + fileName);

// 建議：由 Path 組合每一層
Path correct = Path.of("workspace").resolve(category).resolve(fileName);
```

常用的 Path operation 如下：

| API | 用途 | 範例 |
|---|---|---|
| `resolve(other)` | 將 child path 接到目前 path 後面 | `root.resolve("notes/io.md")` |
| `resolveSibling(other)` | 以同一個 parent 替換檔名 | `file.resolveSibling("tmp.md")` |
| `normalize()` | 消除 `.` 與可化簡的 `..` | `a/./b/../c` → `a/c` |
| `toAbsolutePath()` | 轉成 absolute path | `relative.toAbsolutePath()` |
| `relativize(other)` | 求兩個 path 間的相對路徑 | `root.relativize(file)` |
| `getFileName()` | 取得最後一段 | `io.md` |
| `getParent()` | 取得 parent path | `notes/java` |

`normalize()` 只處理路徑字面結構，不會檢查檔案是否真的存在。`toRealPath()` 才會存取 file system、解析實際路徑，並可能因檔案不存在而丟出 `IOException`。兩者不要混為一談。

### Workspace 路徑安全

若使用者提供 `relativePath`，不能直接：

```java
Path target = workspace.resolve(relativePath);
```

因為 `../outside.md` 可能逃出 workspace。基本的安全模式是先把根目錄與目標都轉成 absolute normalized path，再確認目標仍然位於 root 底下：

```java
static Path resolveInside(Path workspace, String relativePath) {
    Path root = workspace.toAbsolutePath().normalize();
    Path target = root.resolve(relativePath).normalize();

    if (!target.startsWith(root)) {
        throw new IllegalArgumentException("Path escapes workspace: " + relativePath);
    }
    return target;
}
```

這段檢查是檔案型應用程式的重要邊界。實務上還要決定是否允許 symbolic link、是否允許檔名中的特殊字元、檔案大小上限與寫入權限；不要只依賴副檔名判斷內容安全。

## 3. `Files`：對 Path 執行檔案操作

`Files` 是一個只提供 static methods 的 utility class，用來操作檔案、目錄與其他 file types。[3] 最常見的 API 可以分成檢查、建立、讀寫與管理四組。

### 檢查檔案與目錄

```java
if (Files.exists(path)) {
    System.out.println("exists");
}

boolean regularFile = Files.isRegularFile(path);
boolean directory = Files.isDirectory(path);
boolean readable = Files.isReadable(path);
boolean writable = Files.isWritable(path);
long bytes = Files.size(path);
```

`exists()`、`isReadable()` 等檢查與真正操作之間可能有時間差；因此不要把「先檢查」當成完整的 permission 或 race-condition 保證。真正操作時仍要處理 `IOException` 與具體例外。

### 建立目錄與檔案

`createDirectory` 只建立單一層；`createDirectories` 會一併建立不存在的 parent directories。建立新檔案時，`createFile` 在檔案已存在時會失敗：

```java
Files.createDirectories(Path.of("workspace", "java"));
Files.createFile(Path.of("workspace", "java", "io.md"));
```

如果「檔案已存在」是正常情況，通常直接使用 `Files.writeString` 或 `newBufferedWriter`，並選擇清楚的 open options，而不是先 `exists` 再決定。

### 複製、移動與刪除

```java
Path source = Path.of("draft.md");
Path backup = Path.of("draft.md.bak");
Path published = Path.of("published.md");

Files.copy(source, backup, StandardCopyOption.REPLACE_EXISTING);
Files.move(backup, published, StandardCopyOption.REPLACE_EXISTING);
Files.deleteIfExists(published);
```

`copy` 與 `move` 是否能跨 file system、是否保留 attributes，以及 symbolic link 的處理方式，都要參考對應 provider 與 `CopyOption`。若是重要原稿，先寫入同一個目錄的 temporary file，再用 `move` 替換，通常比直接覆寫更容易建立 recovery strategy。

### 列出目錄與掃描 Markdown

`Files.list` 與 `Files.walk` 會回傳 Stream，因此也要管理它們的生命週期；它們不是普通的 `List<Path>`：

```java
try (Stream<Path> files = Files.walk(workspace)) {
    List<Path> markdownFiles = files
            .filter(Files::isRegularFile)
            .filter(path -> path.toString().endsWith(".md"))
            .sorted()
            .toList();

    markdownFiles.forEach(System.out::println);
}
```

`Files.walk` 會遞迴探索子目錄，資料量很大時要注意 traversal 成本與 handle 關閉。若只需要第一層，可使用 `Files.list`：

```java
try (Stream<Path> children = Files.list(workspace)) {
    children.filter(Files::isDirectory).forEach(System.out::println);
}
```

## 4. 文字檔案與 byte 檔案

### 為什麼文字與 byte 要分開？

檔案系統保存的是 bytes；文字檔案需要透過 `Charset` 將 bytes decode 成 characters，寫入時再 encode 回 bytes。UTF-8 是現代 Java 專案與 Markdown 常用的明確選擇，但不能假設所有外部檔案都一定使用 UTF-8；要依資料格式與協定決定。

```java
String markdown = Files.readString(path, StandardCharsets.UTF_8);
Files.writeString(path, markdown, StandardCharsets.UTF_8);
```

不要在跨平台檔案格式中依賴作業系統的預設 charset：

```java
// 不夠明確：charset 由環境決定
String text = Files.readString(path);

// 建議：格式明確使用 UTF-8
String text = Files.readString(path, StandardCharsets.UTF_8);
```

設定檔、Markdown、JSON、CSV 與程式產生的文字檔通常應在規格中固定編碼。若要處理使用者上傳的檔案，應查明來源編碼或提供明確的 charset 選項；錯誤解碼可能造成文字損壞，而不是單純的排版問題。

### 小檔案便利 API

`Files.readString` 與 `Files.writeString` 適合內容大小可控的文字檔案，例如單篇 Markdown 或小型設定檔：

```java
static String loadMarkdown(Path path) throws IOException {
    return Files.readString(path, StandardCharsets.UTF_8);
}

static void saveMarkdown(Path path, String markdown) throws IOException {
    if (path.getParent() != null) {
        Files.createDirectories(path.getParent());
    }
    Files.writeString(
            path,
            markdown,
            StandardCharsets.UTF_8,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING,
            StandardOpenOption.WRITE
    );
}
```

這種 API 會把整個內容載入記憶體。對 JavaBase 單篇 Markdown 很實用；若檔案可能非常大，改用 buffered line-by-line 讀取、byte stream 或 channel，並設計大小上限。

## 5. `InputStream` 與 `OutputStream`：byte I/O

### `InputStream`：讀取 bytes

`InputStream` 是 byte input 的抽象基底類別。它適合圖片、壓縮檔、ZIP、Minecraft 資源、網路 payload 或任何不應先當成文字 decode 的內容。[4]

```java
static byte[] loadBytes(Path path) throws IOException {
    try (InputStream input = Files.newInputStream(path)) {
        return input.readAllBytes();
    }
}
```

`read()` 一次回傳一個 byte 的整數值，讀到結尾回傳 `-1`。直接逐 byte 處理通常效率較低，也要正確處理 unsigned byte；初學時可優先使用 `readAllBytes()` 或 buffer。

### `OutputStream`：寫入 bytes

`OutputStream` 是 byte output 的抽象基底類別。使用 `write(byte[])` 將一批 bytes 寫出；關閉 stream 前資料可能仍停留在 buffer 或 OS layer，因此要用 try-with-resources。

```java
static void saveBytes(Path path, byte[] data) throws IOException {
    if (path.getParent() != null) {
        Files.createDirectories(path.getParent());
    }

    try (OutputStream output = Files.newOutputStream(
            path,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING,
            StandardOpenOption.WRITE
    )) {
        output.write(data);
    }
}
```

`Files.newInputStream` 與 `Files.newOutputStream` 建立的 stream 本身不保證 buffered；大量小筆讀寫時可以包上 `BufferedInputStream` 或 `BufferedOutputStream`：

```java
try (InputStream input = new BufferedInputStream(Files.newInputStream(source));
     OutputStream output = new BufferedOutputStream(Files.newOutputStream(target))) {
    input.transferTo(output);
}
```

`transferTo` 適合把 byte input 複製到 output；它不會把 bytes 轉成文字，也不會替你驗證檔案格式或內容安全。

### Byte I/O 的 Markdown 情境

Markdown 本質上是文字，但 ZIP backup、圖片、附件與 compressed export 是 byte data。不要對 ZIP 或 PNG 使用 `Reader`，也不要對 UTF-8 Markdown 只做 byte slicing 後假設每個 byte 都是一個字元。

| 資料 | 優先 API |
|---|---|
| Markdown、JSON、設定檔 | `Reader`／`Writer` 或 `Files.readString`／`writeString` |
| 圖片、ZIP、PDF、壓縮資料 | `InputStream`／`OutputStream` |
| 需要自訂 seek 或高階效能 | `FileChannel`／其他 channel API |

## 6. `Reader` 與 `Writer`：character I/O

### `Reader`：讀取文字 characters

`Reader` 是 character input 的抽象基底類別。它建立在「已經知道如何把 bytes decode 成 characters」的層級上，適合文字檔案與逐字元／逐行處理。[5]

```java
static String loadText(Path path) throws IOException {
    StringBuilder text = new StringBuilder();

    try (Reader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
        char[] buffer = new char[4096];
        int length;
        while ((length = reader.read(buffer)) != -1) {
            text.append(buffer, 0, length);
        }
    }
    return text.toString();
}
```

### `Writer`：寫入文字 characters

`Writer` 是 character output 的抽象基底類別。它會把 characters encode 成檔案或其他 output destination 使用的 bytes；使用時要明確指定 charset 的底層實作，例如 `Files.newBufferedWriter(path, UTF_8, ...)`。[6]

```java
static void saveText(Path path, String text) throws IOException {
    try (Writer writer = Files.newBufferedWriter(
            path,
            StandardCharsets.UTF_8,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING,
            StandardOpenOption.WRITE
    )) {
        writer.write(text);
    }
}
```

如果不需要逐段處理，`Files.readString`／`writeString` 會比自己建立 `Reader`／`Writer` 更簡單。當檔案需要逐行處理、資料量較大或要串接多段文字時，才切換到 buffered character I/O。

## 7. `BufferedReader` 與 `BufferedWriter`

### 為什麼需要 buffer？

`BufferedReader` 與 `BufferedWriter` 在 Reader／Writer 外包一層 buffer，減少大量細小 I/O 呼叫，並提供適合文字處理的便利方法。buffer 不會改變文字語意，也不會自動修復錯誤 charset；它主要改善存取方式與 API 使用體驗。

### `BufferedReader`：逐行讀 Markdown

```java
static List<String> readLines(Path path) throws IOException {
    try (BufferedReader reader = Files.newBufferedReader(
            path,
            StandardCharsets.UTF_8
    )) {
        return reader.lines().toList();
    }
}
```

`reader.lines()` 回傳 Stream，必須在 `try` 區塊內消費；不要把 Stream return 出去後才關閉 `BufferedReader`，那會留下已關閉或失效的資源。

需要逐行保留控制權時可使用 `readLine()`：

```java
static void printHeadings(Path path) throws IOException {
    try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
        String line;
        while ((line = reader.readLine()) != null) {
            if (line.startsWith("#")) {
                System.out.println(line);
            }
        }
    }
}
```

### `BufferedWriter`：逐行寫 Markdown

```java
static void writeMarkdown(Path path, List<String> lines) throws IOException {
    if (path.getParent() != null) {
        Files.createDirectories(path.getParent());
    }

    try (BufferedWriter writer = Files.newBufferedWriter(
            path,
            StandardCharsets.UTF_8,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING,
            StandardOpenOption.WRITE
    )) {
        for (String line : lines) {
            writer.write(line);
            writer.newLine();
        }
    }
}
```

`newLine()` 會使用 writer／環境定義的換行方式；若 Markdown 內容需要固定使用 LF，應在資料格式層明確規範，或先建立完整字串後用 `Files.writeString` 寫入。不要把跨平台 newline 差異誤認成 Markdown 語意錯誤。

### Buffered I/O 的 decorator 關係

```text
Path
  ↓ Files.newBufferedReader(path, UTF_8)
BufferedReader
  ↓ extends
Reader
  ↓ decode／讀取 characters
File system
```

byte I/O 也有相同的包裝思考：

```text
Path
  ↓ Files.newInputStream(path)
InputStream
  ↓ optional BufferedInputStream
buffered byte reading
```

`BufferedReader` 與 `BufferedWriter` 不是另一種檔案格式；它們是包裝底層 I/O 的工具。這種 decorator 結構會在 Java API、Minecraft resource loader、ZIP 處理與網路程式裡反覆出現。

## 8. try-with-resources：一定要關閉資源

只要物件實作 `AutoCloseable`，就可以放在 try-with-resources 中。`InputStream`、`OutputStream`、`Reader`、`Writer`、`BufferedReader`、`BufferedWriter` 與由 `Files.walk`／`Files.list` 建立的 Stream 都應依其生命週期正確關閉。

```java
try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String firstLine = reader.readLine();
    System.out.println(firstLine);
} // 自動 close，即使區塊中丟出例外
```

不建議手動寫：

```java
Reader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8);
try {
    // read
} finally {
    reader.close();
}
```

手動 `finally` 容易在建立多個資源、處理 close exception 或中途建立失敗時寫錯。try-with-resources 也會保留 suppressed exception，讓除錯資訊比簡單吞掉 close 例外更完整。

多個資源會依相反建立順序關閉：

```java
try (InputStream input = Files.newInputStream(source);
     OutputStream output = Files.newOutputStream(target)) {
    input.transferTo(output);
}
```

## 9. 本地 Markdown Workspace 實戰

### 讀取單篇 Markdown

JavaBase 的核心資料模型是「Markdown 是唯一真實來源，索引可以重建」。如果用 Java 寫一個簡化版 reader，可以將檔案讀取、UTF-8 與 front matter 解析分成不同責任：

```java
record MarkdownDocument(Path path, String frontMatter, String body) {}

static MarkdownDocument readMarkdown(Path path) throws IOException {
    String content = Files.readString(path, StandardCharsets.UTF_8);
    int separator = content.indexOf("\n---\n", 4);

    if (!content.startsWith("---\n") || separator < 0) {
        return new MarkdownDocument(path, "", content);
    }

    String frontMatter = content.substring(4, separator);
    String body = content.substring(separator + "\n---\n".length());
    return new MarkdownDocument(path, frontMatter, body);
}
```

這只是教學用的最小分割器，不是完整 YAML parser。正式應用要處理 CRLF、front matter 中的 `---`、Unicode、錯誤 metadata 與檔案大小上限；不要把示意 parser 直接當成所有 Markdown 語法的完整實作。

### 掃描並建立可重建索引

```java
record MarkdownIndexEntry(Path path, String title, String searchText) {}

static List<MarkdownIndexEntry> scanMarkdown(Path workspace) throws IOException {
    try (Stream<Path> paths = Files.walk(workspace)) {
        return paths
                .filter(Files::isRegularFile)
                .filter(path -> path.getFileName().toString().endsWith(".md"))
                .map(path -> {
                    try {
                        String content = Files.readString(path, StandardCharsets.UTF_8);
                        String title = path.getFileName().toString();
                        return new MarkdownIndexEntry(path, title, content);
                    } catch (IOException error) {
                        throw new UncheckedIOException(error);
                    }
                })
                .toList();
    }
}
```

這個例子把 Markdown 檔案當作 source，把 `MarkdownIndexEntry` 當作可丟棄的 derived index。若 index 壞掉，可以重新掃描檔案。這與 JavaBase 的 Markdown-first 架構相同：不要把索引資料誤當成原稿。

實務上若要在 pipeline 中傳遞 checked `IOException`，可以在邊界包成 `UncheckedIOException`，並在外層統一處理；也可以使用一般 `for` loop，讓錯誤位置更直接。Stream 不是唯一正確答案。

### 安全寫入 Markdown 原稿

安全寫入至少要包含四個步驟：限制目標路徑在 workspace 內、建立 parent directory、使用 UTF-8、寫入失敗時保留舊檔或 backup。最小示意如下：

```java
static void writeWorkspaceMarkdown(
        Path workspace,
        String relativePath,
        String markdown
) throws IOException {
    Path target = resolveInside(workspace, relativePath);

    if (!target.getFileName().toString().endsWith(".md")) {
        throw new IllegalArgumentException("Only Markdown files are allowed");
    }

    Files.createDirectories(target.getParent());
    Files.writeString(
            target,
            markdown,
            StandardCharsets.UTF_8,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING,
            StandardOpenOption.WRITE
    );
}
```

較高可靠度的 writer 可以先寫入同一個目錄的 temporary file，確認寫入成功後再 `move` 替換；若需要 crash consistency，還要研究 `FileChannel.force`、atomic move 是否被當前 file system provider 支援，以及 backup／revision 策略。這些是資料可靠度設計，不是單靠 `BufferedWriter` 就能自動得到的保證。

### 讀寫與索引的責任分離

```text
Markdown file
    ↓ Files.readString / BufferedReader
Parser
    ↓ title、tags、body
Derived index
    ↓ searchText、tags、graph edges
Search / UI
```

`Files` 只負責檔案系統操作；parser 只負責把文字轉成文件模型；indexer 只負責建立可重建索引。把這三層混在一個 method 中，會讓「檔案寫成功但索引失敗」或「索引存在但原稿遺失」變得難以診斷。

## 10. Minecraft Java 的 I/O 對照

Minecraft mod 常會處理 resource、config、datapack、JSON、NBT、世界資料或模組匯出檔。Java I/O 的 byte／character 概念是共通的，但 loader 如何提供 resource、何時可存取 world、config 放在哪裡，以及 server／client thread contract 都由 Fabric、NeoForge 或其他平台決定。

| 情境 | Java I/O 層 | Minecraft 注意事項 |
|---|---|---|
| 讀取 JSON／Markdown／設定文字 | `Reader`／`BufferedReader` | 固定 charset，驗證內容與大小 |
| 讀取圖片、ZIP、壓縮資源 | `InputStream`／`BufferedInputStream` | 不要把 bytes 直接當文字 |
| 寫入 mod config | `Writer`／`BufferedWriter` 或 `Files.writeString` | 遵循 loader 的 config directory 與 lifecycle |
| 讀取 resource | 通常是 `InputStream` | resource 可能來自 jar，不一定是普通可寫 Path |
| 匯出 backup | `OutputStream`／ZIP API | 處理路徑、檔案大小與權限 |
| 背景載入 | I/O + executor | 不能從背景 thread 任意修改 world／entity |

不要假設一個 `Path` 一定可以拿來寫入 mod resource；jar 內 resource 常常只提供 input stream。也不要在 server tick 中對整個世界做未限制的檔案掃描。先查對應 loader 的 resource、config、lifecycle 與 thread 文件，再決定 Java I/O API 的使用位置。

## 11. 常見錯誤

| 錯誤 | 為什麼有問題 | 改法 |
|---|---|---|
| 用字串拼路徑 | 分隔符號、`..` 與跨平台行為容易出錯 | 使用 `Path.resolve()` 與 `normalize()` |
| 把 `Path` 當成檔案內容 | Path 只描述位置，不會自動讀檔 | 使用 `Files.readString`、`newBufferedReader` 或 stream |
| 沒指定 charset | 不同環境可能用不同預設編碼 | 對 Markdown／JSON 明確使用 `StandardCharsets.UTF_8` |
| 用 Reader 讀 ZIP 或圖片 | binary bytes 不應直接 decode 成文字 | 使用 `InputStream`／`OutputStream` |
| 讀取後沒有 close | 可能留下 file handle、buffer 或 directory resource | 使用 try-with-resources |
| 把 `Files.walk()` 當成普通 List | 它回傳需要關閉的 Stream | 在 try-with-resources 中消費 |
| `exists` 後才寫入並以為安全 | 檢查與操作之間可能有 race | 直接操作並處理例外，必要時使用明確 open options |
| 讓使用者路徑直接 resolve | `../` 可能逃出 workspace | absolute + normalize + `startsWith(root)` |
| 直接覆寫唯一原稿 | 寫入中斷可能損失資料 | temporary file、backup、revision 與 move 策略 |
| 把 `BufferedWriter` 當成 atomic write | buffer 只處理 I/O 效率，不保證 crash consistency | 另設計 temporary／replace／recovery 流程 |
| 把 jar resource 當可寫檔案 | resource 可能沒有一般檔案系統位置 | 依 API 取得 InputStream，另選 config／data directory |
| 在背景 thread 直接碰 Minecraft world | 可能違反 thread contract | I/O 與遊戲狀態更新分離，再安全排回正確 thread |
| 為了 Stream 而犧牲可讀性 | checked exception 與 lifecycle 會變複雜 | 必要時使用普通 loop 與明確錯誤處理 |

## 12. 練習

### 練習一：Markdown reader

使用 `Path` 與 `Files.readString` 讀取一篇 UTF-8 Markdown，檢查檔案不存在、是否為 regular file，並輸出 front matter 與 body 的字數。請把 `IOException` 轉成使用者可以理解的錯誤訊息。

### 練習二：BufferedReader 標題掃描

使用 `BufferedReader` 與 `readLine()` 掃描目錄中所有 `.md` 檔案，只收集以 `# ` 開頭的第一級標題。要求每個 `Files.walk` 與 `BufferedReader` 都在 try-with-resources 中關閉。

### 練習三：Workspace 安全路徑

實作 `resolveInside(workspace, relativePath)`，測試 `java/io.md`、`./java/io.md`、`../outside.md`、絕對路徑與含有 symbolic link 的情況。說明 `normalize()`、`toAbsolutePath()` 與 `toRealPath()` 的差異。

### 練習四：安全寫入與 revision

先使用 `BufferedWriter` 寫入 temporary Markdown，再使用 `Files.move` 搭配適當的 `CopyOption` 替換正式檔案。模擬寫入失敗，確保舊檔仍可被讀取；再把舊檔複製成 revision backup。

### 練習五：Minecraft resource review

選擇 Fabric 或 NeoForge 的一個 resource／config 讀取情境，查明它回傳的是 `InputStream`、`Path` 還是其他 API。說明為什麼不能直接把 jar resource 當成可寫檔案，並把 Java 共通 I/O 與 loader-specific lifecycle 分成兩段。

## 13. 複習速查

```text
檔案位置
  Path.of(...)
    ↓ resolve / normalize / startsWith(root)
實際檔案操作
  Files.exists / createDirectories / copy / move / delete
    ↓
文字資料
  Files.readString / writeString
  或 Reader → BufferedReader
  或 Writer → BufferedWriter
    ↓
二進位資料
  InputStream → BufferedInputStream
  OutputStream → BufferedOutputStream
    ↓
資源生命週期
  try-with-resources
```

| 我想做什麼 | 優先考慮 |
|---|---|
| 表達檔案位置 | `Path` |
| 建立、檢查、移動或刪除檔案 | `Files` |
| 讀取小型 UTF-8 Markdown | `Files.readString(path, UTF_8)` |
| 寫入小型 UTF-8 Markdown | `Files.writeString(path, text, UTF_8, ...)` |
| 逐行讀文字 | `BufferedReader` |
| 逐行寫文字 | `BufferedWriter` |
| 讀取圖片、ZIP、壓縮資料 | `InputStream` |
| 寫入 binary export | `OutputStream` |
| 掃描目錄樹 | `Files.walk`，並關閉回傳 Stream |
| 資源自動關閉 | try-with-resources |
| 使用者提供相對路徑 | `absolute + normalize + startsWith(root)` |
| 本地 Markdown Workspace | Markdown 原稿、parser、derived index 分層 |
